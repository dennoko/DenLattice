# DenLattice 要件定義

`requirements.md` のラフを整理し、類似ツール調査の結果を反映した要件定義。

VRChat アバター改変向けの、**非破壊ラティス（FFD）変形ツール**。
dennoko Mesh Editor（以下 DME）と同じコンセプト・同じ NDMF 連携構成を持ち、**頂点の動かし方だけをラティスに差し替えたもの**として設計する。

---

## 1. コンセプト

DME の 5 原則をそのまま引き継ぐ。

| 原則 | 意図 |
| --- | --- |
| 簡単 | 制御点を掴んで動かす、それ以上の学習コストを要求しない |
| シンプル | 機能を絞る。設定項目を増やさない |
| 軽量 | 外部 dll に依存しない。シーンロード・ドメインリロードを重くしない |
| 非破壊 | 元メッシュアセットを一切書き換えない。編集内容はコンポーネントに保持 |
| 効率化 | 「開く → 動かす → 閉じる」で完結。保存操作を挟ませない |

### 本ツール固有の中核価値

**格子数を後から変えても、今の形が崩れない。**

通常のラティスツールは変形情報を「制御点の位置」として持つため、格子数を変えると変形が失われる（あるいは一度モディファイアを適用＝確定させる必要がある）。DenLattice は**変形の実体を頂点ごとのデルタとして保持する**ため、

- 3×3×3 でざっくり寄せる → 5×3×5 に増やして局所を詰める → さらに 3×3×3 に戻す

を、いつでも・何度でも・形を崩さずに往復できる。これが DME に対する差別化点であり、後述するデータモデル（§7）と格子数変更の仕様（§6.4）がその実装上の担保になる。

### DME との棲み分け

| | 得意 | |
| --- | --- | --- |
| DenMeshEditor | 頂点単位のピンポイント修正（食い込み、めり込みの一点直し） | 局所 |
| **DenLattice** | 領域全体のなだらかな変形（胸・尻・腿を丸ごと太らせる／細らせる） | 広域 |

同じアバターに両方を載せられること（NDMF パイプライン上で衝突しないこと）を要件とする。

## 2. 対象環境

- **Unity 2022.3.22f1 以降**（Unity 6 以降まで対応）
- VRChat SDK (com.vrchat.avatars) — ターゲットは VRC ユーザー
- **NDMF (nadena.dev.ndmf) 必須** — 検証基準は 1.11.0（DME と同じ）
- Modular Avatar との併用前提（MA Scale Adjuster などの影響下で編集できること）

## 3. 類似ツール調査

| ツール | 位置づけ | 取り入れる点 | 取り入れない点 |
| --- | --- | --- | --- |
| [Mesh Deformation Tool（みつばや）](https://booth.pm/ja/items/7488375) ¥1,000 | NDMF 対応。ラティス／ブラシ／頂点編集の 3 種を搭載した高機能ツール | X/Y/Z ごとの対称編集、制御点の矩形選択、BlendShape 出力 | レイヤースタック、ボーンウェイト再計算、測地線フォールオフ、ブラシ／頂点編集（DME の担当） |
| [Uni-Lattice（すぺいす）](https://booth.pm/ja/items/7393100) ¥800 | ラティス特化。SMR / MeshFilter 両対応、BlendShape 保持 | MeshFilter 対応、シェイプキー化出力 | クローン生成方式（＝非 NDMF。本ツールは NDMF プレビュー方式） |
| [Blender Lattice モディファイア](https://docs.blender.org/manual/en/3.6/animation/lattice.html) | 業界標準の挙動リファレンス | 補間方式（Linear / B-Spline / Catmull-Rom）、U/V/W 個別の解像度指定 | U/V/W ごとに**別々の**補間方式を選ぶ機能（設定過多）、頂点グループによる影響制御 |

**調査からの結論：** ラティス機能そのものは既に競合が存在する。差別化は機能量ではなく **「格子数を自由に変えられる」＋「操作手数の少なさ」＋「軽さ」** に置く。Mesh Deformation Tool の上位互換を目指さない。

## 4. 用語

| 用語 | 意味 |
| --- | --- |
| 元メッシュ | `SkinnedMeshRenderer.sharedMesh` / `MeshFilter.sharedMesh` のアセット |
| プロキシ | NDMF プレビューが生成する、他ツールの改変が適用済みの一時 Renderer |
| ラティスボックス | 変形の作用範囲を定める直方体。位置・回転・サイズを持つ |
| 制御点 | ラティスボックスを resU×resV×resW に分割した格子点。掴んで動かす対象 |
| 制御点オフセット | 制御点の**変位**（格子位置からのずれ）。ボックスローカル空間で保持する |
| 頂点デルタ | 頂点ごとの移動量（`Vector3`）。**変形の実体はこちら**で、プレビューもビルドもこれだけを見る |
| パラメータ化 | 各頂点のボックス内座標 (u,v,w)。ボックスか対象が変わるまで固定される |
| レスト位置 | 自分の変形を取り除いた頂点位置（`WorldVertices − skin·delta`）。パラメータ化の基準 |
| ベイク | 変形を適用した Mesh アセットをディスクへ書き出す操作 |

## 5. スコープ

### やること

- ラティスボックスの配置と、制御点によるメッシュ変形
- 変形を保ったままの格子数変更（中核機能）
- 補間方式の切り替え（三線形 / B-Spline / Catmull-Rom）
- 軸指定のミラー編集
- 複数 Renderer の同時変形（服と素体をまとめて）
- NDMF プレビューへの反映 と ビルド時の非破壊適用
- ベイク（メッシュアセット書き出し／シェイプキー化）
- Undo / Redo

### やらないこと（意図的な非対応）

- トポロジ編集（頂点・辺・面の追加／削除）
- 頂点単位の直接編集・ブラシ変形 → **DME の担当**
- UV / 法線 / ウェイトの手編集、ボーンウェイト再計算
- 複数ラティスの同時保持（レイヤースタック）。1 コンポーネント = 1 ボックス
- U/V/W ごとに別々の補間方式を選ぶ機能
- 制御点のアニメーション、シェイプキーとしての制御点保持
- 法線・接線の再計算（DME と同じく、元の値を保持）
- 編集中の選択アウトライン／選択ワイヤーフレームの自動抑制

トポロジを変えないことは仕様上の重要な前提であり、頂点インデックス基準のデルタが成立する条件でもある。

---

### 選択アウトライン抑制を撤去した理由

Unity 全体の永続設定を書き換える方式は、エディタが落ちると OFF のまま残る副作用がある。
Renderer 単位で選択ワイヤーフレームを隠す方式も、選択変更のたびに再適用する常駐処理が必要になる。
見た目の改善に対して副作用と保守コストが見合わないため、DennokoMeshEditor と同様に撤去した。
編集中に変形前の輪郭が重なる場合は、Scene ビューの Gizmos メニューで Selection Outline / Selection Wire を切り替える。

## 6. 機能要件

### 6.1 ラティスボックス

- 位置 / 回転 / サイズ を持つ直方体。**アバタールートのローカル空間**で保持する（複数 Renderer を跨ぐため共通基準が必要。取れない場合はコンポーネントの Transform にフォールバック）
- **シーン階層に GameObject を作らない。**コンポーネントのシリアライズ値 + シーンビューのハンドルで扱う（Prefab を汚さない）
- 初期配置は**対象 Renderer 群のバウンディングボックスへ自動フィット**（少し余白を持たせる）。コンポーネント追加直後から使える状態にする
- 編集中はシーンビューの TRS ハンドルで移動・回転・スケールできる
- ボックス外の頂点は**変形しない**（変位ゼロ）。Blender の Linear 補間のような外挿はしない — アバター全体が意図せず歪むのを防ぐ

### 6.2 制御点の選択と移動

- 制御点はシーンビューにドットで描画。格子のワイヤーフレームも描き、構造を読み取れるようにする
- **クリック選択**（最も近い制御点。同距離なら手前を優先）と、**矩形選択による複数選択**
  - 制御点は空間中に浮いているため、DME のような深度バッファによる遮蔽消去は**行わない**（体内の制御点が掴めなくなるため）。代わりに、メッシュに隠れた制御点は減光して描く
- 選択した制御点を移動ハンドル（`Handles.PositionHandle`）でドラッグして変形する
- 複数選択時は全点が同じ変位 D を受け取る
- 制御点の回転・スケールは v1 では非対応（Mesh Deformation Tool にはあるが、「1 ハンドル = 1 変位」の操作モデルを崩すため見送り）
- 選択解除は Esc、もう一度 Esc で編集終了（DME と同じ）
- 「制御点をリセット」ボタン — ラティス層を破棄して制御点を格子位置へ戻す（確定済み頂点デルタは残る）

**実装上の要点：DME のプロポーショナル編集と構造が同じ。**
DME は (中心 C, 半径 r, 減衰 f) から頂点ごとの重み w(v) を作り、`vertex = snapshot + w(v)·D` で変形していた。DenLattice は w(v) を**基底関数の値**に差し替えるだけで、それ以外（スナップショット、ドラッグ中の再計算、確定処理、Undo）はそのまま流用できる。

- 重み w(v) はドラッグ開始時に一度だけ計算してキャッシュする。ドラッグ中は変わらない（制御点が動いてもボックスは動かないため）
- 影響を受ける頂点は基底の台（サポート）内に限られる。三線形なら隣接 2 セル、三次なら隣接 4 セル分だけを走査すればよく、全頂点を毎回見る必要はない

### 6.3 補間方式

Inspector で切り替える。**既定は三線形補間。**

| 方式 | 性質 | 用途 |
| --- | --- | --- |
| **Trilinear（三線形）** — 既定 | 制御点を通る。影響範囲が狭く、動かした点の周りだけが動く | 局所を確実に動かしたいとき |
| **B-Spline（三次）** | 制御点を通らない（近似）。最も滑らか。制御点を D 動かしてもメッシュは D より小さく動く | 全体をなめらかに膨らませたいとき |
| **Catmull-Rom（三次）** | 制御点を通る（補間）。B-Spline より滑らかさは劣るが、動かした量がそのまま出る | 滑らかさと直感の両立 |

- 3 方式はいずれもテンソル積基底であり、**基底行列が違うだけで評価コードは共通**にできる。実装量は 1 本分
- **変位空間で定式化する。**`deform(v) = v + Σ B_i(v)·d_i`（d_i は制御点の**変位**）とし、位置空間の FFD（`Σ B_i(v)·P_i`）は使わない
  - こうすると「全 d_i = 0 なら恒等変換」が基底の性質によらず厳密に成り立つ。B-Spline が制御点を通らないことも、境界で基底の和が 1 にならないことも問題にならない
  - 頂点デルタとして持つというデータモデル（§7）とも自然に噛み合う
- 三次基底は各軸 4 点のステンシルを要求する。**端は最外殻の制御点を複製して拡張する**（clamped）。ある軸の解像度が 2 の場合、その軸だけ線形へ縮退させる
- 補間方式の切り替えは**確定済みの形状を変えない**（変形の実体は頂点デルタで、そこに補間方式は残っていない）。効くのは次のドラッグからで、同じ制御点の動かし方でも広がり方が変わる

### 6.4 格子数の変更 — 本ツールの中核

- U / V / W ごとに個別指定。**既定 3×3×3**
- 範囲は各軸 **2〜10**（10³ = 1000 制御点。これ以上はハンドル描画とピッキングが実用的でなくなる）
- **編集中のオーバーレイから変更できる**こと。Inspector からも変更できる
- 軸名（U / V / W）を明示し、± ボタンで 1 ずつ増減できること。数値の直接入力も残す

#### 変更時の処理

格子数を変えても**画面上の形状は 1 mm も動かない**ことを要件とする。

**これは自動的に成立する。**変形の実体は既に頂点デルタとしてコンポーネントに入っており（§7）、制御点オフセットは変形結果に一切関与しないため、格子数を変えても適用されるデルタは 1 バイトも変わらない。したがって処理は次の 1 行で足りる。

```
制御点オフセットを破棄し、新しい格子数でケージを組み直す
```

- **制御点はボックスの格子位置へ戻す。**旧いケージの形を新しい格子でサンプリングし直すこともできるが、そうすると「格子を細かくしたのに、ケージが歪んだままでどこを掴めばいいのか分からない」状態になる。オフセットは足場でしかなく、捨てても形状は失われないので、毎回まっさらな格子から掴み直せる方を採る（§12 A）
- 頂点のパラメータはボックス基準（§7.4）なので、格子数を変えても取り直す必要がない
- 選択は捨てる（制御点インデックスの意味が変わるため）
- 一連の操作は Undo 1 段にまとめる

#### ボックスの移動・回転・スケール時

変位場はボックスに紐づいているため、**ボックスの Transform を変えたときは制御点オフセットをゼロへ戻し**、新しいパラメータ化を取り直す。ここでも頂点デルタには触れないので**形状は変化しない**。ボックスを動かしてもメッシュが引きずられない、という直感どおりの挙動になり、「別の部位へボックスを移して続きを変形する」という使い方がそのまま成立する。

ドラッグ中はコンポーネントへ書き込まず、未確定値でボックスとケージを描く（離した瞬間にケージが飛ばないよう、ドラッグ中から「オフセットがゼロに戻った状態」を見せる）。確定は Undo 1 段。

### 6.5 ミラー

- **ラティスボックスのローカル軸を基準**とする。ミラー軸は U / V / W から選択（既定 U）
- 制御点 (i,j,k) の相手は同じボックス内の (res-1-i, j, k)。**変位 D も軸成分を反転する**
  - DME の「仮想中心」方式と違い、格子は離散インデックスなので相手探索が自明。許容誤差というパラメータが要らない
- **中心列の扱い**（解像度が奇数のとき i = (res-1)/2 は自分自身が相手）
  - 適用する変位を `(D + R·D)/2`、すなわち **D のミラー面に平行な成分のみ**とする
  - こうすると軸方向成分は打ち消され、面内成分は 2 倍にならない。中心の制御点はミラー面上を滑るようにしか動かなくなり、これが対称編集として正しい挙動
- アバターの左右対称編集をしたい場合、ボックスをアバタールートの `x = 0` 平面に中心を合わせて配置する必要がある。**「中心へ」ボタン**（Inspector）を用意して 1 クリックで揃えられるようにする
- ミラー ON/OFF と軸の選択は**編集中のオーバーレイから**変更できること
- 反対称（アンチシンメトリ）モードは v1 では非対応

### 6.6 複数メッシュの同時変形

- 1 コンポーネントで複数の Renderer を対象にできる（`SkinnedMeshRenderer` / `MeshRenderer` 両対応）
- ボックス内の頂点は Renderer を跨いで一括で変形される。**服と素体を同時に馴染ませられること**がラティスを使う最大の動機であり、必須要件とする
- ボックスがアバタールート空間で定義されるため、複数 Renderer への適用は自然に成立する
- Renderer を持つ GameObject にアタッチされた場合、その Renderer を自動で最初の対象に登録する（`Reset()`）

### 6.7 編集中の UI（シーンビューオーバーレイ）

DME と同じ「ドラッグで移動できるパネル」を踏襲し、**編集を中断せずに設定を変えられる**ことを要件とする。

置くのは**編集中に手が止まる操作だけ**に絞る。パネルが大きいほどシーンが隠れ、編集そのものの邪魔になるため、一度決めたら触らない設定（補間方式）とボックスの自動配置（対象に合わせる・中心へ）は Inspector 側にのみ置く。

| 項目 | 種別 |
| --- | --- |
| 格子数 U / V / W | 軸名 + ± ボタン + 数値欄（2〜10） |
| ミラー ON/OFF | トグルボタン（ON で緑） |
| ミラー軸 | U / V / W のボタン |
| ボックス編集モード | トグル（制御点操作 ⇄ ボックスの TRS 操作）＋ 移動 / 回転 / 拡縮 |
| 制御点をリセット | ボタン |
| 操作ヒント | Esc で選択解除／もう一度 Esc で終了 |
| 警告 | NDMF プレビュー未適用時のフォールバック警告 |

- **パネルはラティス・ハンドル・矩形選択より後に描く。**IMGUI は呼んだ順に描くため、先に描くと格子線やハンドルがパネルを突き抜けて文字が読めなくなる。背景もほぼ不透明にする
- パネルの下でハンドルが反応しないよう、当たり判定だけは描画より先に確定させ、カーソルがパネル上にある間は `HandleUtility.AddControl(..., 0f)` でハンドルより手前のコントロールを主張する
- パネルの高さは中身の実測値から決める（行数を定数で持つと、言語やスキンで文字高が変わったときに下端が切れる）
- **ホイールは横取りしない。**DME はハンドルを掴んでいる間ホイールでブラシ半径を変えていたが、ラティスに対応する連続量が無い。シーンビューのズームのまま残す
- Layout / Repaint でレイアウト構成が変わらないよう、警告の有無などは Layout イベント時に固定する（DME で踏んだ `Getting control N's position` 例外の再発防止）

### 6.8 NDMF 連携

**DME の構成をそのまま踏襲する。**リフレクションは使わない。

- `IRenderFilter` / `IRenderFilterNode` を実装し、`OnFrame(original, proxy)` でプロキシ Renderer をプッシュ型で受け取る
- 受け取ったプロキシは `ProxyRegistry` 経由でシーンビュー編集セッションへ渡す
- **編集済みメッシュの生成は世代が変わったときだけ、プロキシへの代入は毎フレーム。**`ProxyObjectController.OnPreFrame` がフレーム冒頭で `sharedMesh` を元 Renderer のものへ戻すため
- `GetTargetGroups` の時点で対象コンポーネントを確定させ、`RenderGroup.WithData` で添付する（`Instantiate` 内でシーンを走査しない = 大量配置時の O(N²) を作らない）
- 監視は `revision` カウンタのみを見る。編集セッション中のコンポーネントは監視対象から外し、未確定の変形は `LiveEdits` 経由で渡す（Undo 連打でパイプライン再構築が積まれるのを防ぐ）
- ビルドは **`BuildPhase.Transforming`**。頂点数を変える Avatar Optimizer（`Optimizing`）より先行する
- フィルタ順序は `.AfterPlugin("nadena.dev.modular-avatar")`
- 処理後、コンポーネントをビルド成果物から削除する
- **プレビュー適用とビルド適用は同一の適用ロジックを共有する**（結果が食い違わないことをコードの共有で保証する）

### 6.9 ベイク

DME と同じ仕様。実行前にラティス層を畳み込む。

| 項目 | 仕様 |
| --- | --- |
| 保存先 | 元メッシュと同一フォルダ |
| 名前 | `<元メッシュ名>_lattice`（既に付いていれば追加しない） |
| 衝突時 | 末尾に スペース + 連番（`Body_lattice 1`, `Body_lattice 2` …） |
| シェイプキー化 | チェックボックス。ON なら元形状を保持し、変形分を新規シェイプキーとして追加 |
| Renderer 差し替え | **行わない。**アセット出力のみ |
| 法線・接線 | 再計算しない |

- 元メッシュが FBX 内のサブアセットの場合、新規 `.asset` として書き出す（FBX は書き換えない）
- 出力後、パスを Console と Inspector に表示し `EditorGUIUtility.PingObject` で選択させる

### 6.10 Undo / Redo

DME と同じ規律。

| 操作 | Undo の粒度 |
| --- | --- |
| 制御点のドラッグ 1 回 | 1 段 |
| 格子数の変更（ケージの組み直し） | 1 段 |
| ボックスの TRS 変更 | 1 段（制御点のリセットを含む） |
| オーバーレイでの設定変更（連続ドラッグ） | `CollapseUndoOperations` で 1 段 |

- 書き込みは `Undo.IncrementCurrentGroup` → `RecordObject` → `FlushUndoRecordObjects` → `IncrementCurrentGroup` の順（`Handles.PositionHandle` が MouseUp を消費するため自動フラッシュに頼らない）
- 空の段を作らない（書き込むものが無ければグループを切らずに抜ける）
- ドラッグ終了の検知は `GUIUtility.hotControl == 0` または `Event.rawType == MouseUp`
- `Undo.undoRedoPerformed` ではフラグを立てるだけにし、実処理は `EditorApplication.update` で 1 フレーム 1 回に間引く（Ctrl+Z 押しっぱなし対策）
- Undo でハンドル位置も戻す。ハンドル位置は `格子位置 + オフセット` で表せるため、プレビューメッシュの再構築完了を待たずに決められる

**DME より有利な点：** 制御点オフセットは最大でも 1000 点 × 12 バイト程度で、頂点デルタと違い巨大にならない。制御点ドラッグの Undo は常に軽い。重いのは格子数変更とボックス移動（畳み込みを伴う）だけで、いずれも頻度が低い。

## 7. データモデル

### 7.1 構成

```csharp
public class DenLattice : MonoBehaviour
{
    // --- 対象と変形の実体 ---
    public List<MeshEdit> edits;          // Renderer ごとの頂点デルタ（byte[] blob + revision）

    // --- ラティスボックス（アバタールート空間） ---
    public Vector3 boxPosition;
    public Quaternion boxRotation;
    public Vector3 boxSize;

    // --- 格子（編集を続けるための足場） ---
    private int resU = 3, resV = 3, resW = 3;
    public InterpolationType interpolation = InterpolationType.Trilinear;
    private byte[] controlOffsets;        // 12 バイト/点、密。ボックスローカル空間

    // --- 設定 ---
    public bool mirror;
    public LatticeAxis mirrorAxis = LatticeAxis.U;
    public bool freezeBorder;
    public bool bakeAsBlendShape;
    public string blendShapeName;
}
```

**最終形状は次の 1 行で決まる。**

```
final(v) = base(v) + delta[v]
```

- `base(v)` … プロキシから読んだ、上流ツール適用済みの形状
- `delta[v]` … 頂点デルタ。**メッシュローカル（バインドポーズ）空間**で保持

**制御点オフセットはこの式に出てこない。**ラティスは「デルタをどう作るか」を決める入力装置であって、出力には関与しない。ドラッグ 1 回ごとに

```
delta[v] ← snapshot[v] + M_v⁻¹ · ( D·Σ_{i∈選択} B_i(v) + R·D·Σ_{i∈ミラー} B_i(v) )
```

として materialize され、マウスを離した時点でコンポーネントへ確定する（`M_v` は頂点のスキニング行列 `Σ wᵢ(Bᵢ·Pᵢ)`、`D` はハンドルのワールド変位、`R` はミラー軸での反射）。

この構造から次が従う。

- **格子数やボックスをいくら変えても形状は変わらない**（§6.4）
- **プレビューとビルドの適用処理は DME と 1 バイトも変わらない**。`outVerts[i] += delta[i]` だけ。ラティスの評価コードはビルドパスに存在しない
- 制御点オフセットは「以前どこまで動かしたか」を覚えておくためだけに保存される

### 7.2 頂点デルタの保持形式

**DME の `MeshEdit` をそのまま流用する。**

- `byte[]` 1 本（16 バイト/頂点：int32 index + float32 x,y,z）+ `revision` カウンタ
  - テキスト YAML で `List<Vector3>` が 1 頂点 4 行に展開されるのを避ける（シーンロード時間）
  - Prefab オーバーライドがプロパティ 1 件で済む（`Array.data[i]` が頂点数 × 2 件積まれない）
  - `revision` だけを見れば変更検出が O(1) で済む（NDMF の `Observe` は抽出関数を毎フレーム再評価する）
- `vertexCount` を記録し、適用前に**プロキシの**頂点数と照合する。不一致なら適用をスキップして Inspector に警告

### 7.3 なぜ任意の上流変形に耐えるのか

適用処理が `outVerts[i] = baseVerts[i] + delta[i]` の 1 行に集約され、`baseVerts` が何であるかを問わないため。シェイプキーとまったく同じ意味論であり、上流が何をしたかを一切推論しない。唯一の前提条件は**頂点数と頂点順序の保存**（§6.8 のビルドフェーズ選択と `vertexCount` 照合で担保する）。

### 7.4 パラメータ化の基準と寿命

各頂点のボックス内座標 (u,v,w) は、**自分の変形を取り除いたレスト位置**から求める。

```
rest[v] = WorldVertices[v] − M_v · delta[v]
```

- 変形後の位置から計算すると、変形するたびに基底の値 B(v) が変わり、**制御点を元の位置へ戻しても形が戻らない**ことになる
- レスト位置基準なら B(v) がセッションを跨いでも変わらないため、「昨日動かした制御点を今日引き戻す」が正しく効く
- デルタは疎なので、引き算が要るのは実際に動かした頂点だけ。全頂点にスキニング行列を作る必要はない

取り直すタイミングは次の 3 つに限る。

| 契機 | 理由 |
| --- | --- |
| セッション開始 / 対象リストの作り直し / 頂点数の変化 | 別のメッシュになっている |
| ボックスの Transform 変更 | 座標系そのものが変わる（同時に制御点オフセットもゼロへ戻る） |
| 上流形状の変化、ただし**制御点がまだ格子上にあるときだけ** | MA Scale Adjuster のスライダー操作などへ追従する。ケージを動かした後は取り直さない（上記の可逆性を壊すため） |

格子数の変更では取り直さない。パラメータはボックス基準であって格子基準ではないため。

## 8. 操作フロー

```
1. アバタールート（または対象メッシュ）にコンポーネントをアタッチ
      └─ ボックスが対象メッシュのバウンズへ自動フィットされる
2. 「編集」ボタン
      ├─ シーンビューが編集モードに入る
      ├─ ボックスを目的の部位へ合わせる（TRS ハンドル）
      ├─ 制御点を選択して動かす
      └─ 必要になったらオーバーレイで格子数を増やす（形は崩れない）
3. 「編集終了」で編集モードを抜ける
4. そのままアップロード → ビルド時に変形が反映される
```

保存ボタンは設けない。編集結果はコンポーネントのシリアライズ対象として保持され、Undo / Prefab / シーン保存の通常フローに乗る。

## 10. 非機能要件

- **ロードコスト：** 外部 dll に依存しない。ドメインリロード時の初期化を最小限に保つ
- **編集レスポンス：** 数万頂点規模でハンドル操作が引っかからないこと
  - 制御点ドラッグ中は、開始時にキャッシュした重みを使うだけ（基底評価は毎フレーム走らせない）
  - 影響頂点の探索は基底の台の内側に限定する。三線形なら 2 セル、三次なら 4 セル分
- **大量配置耐性：** シーンに多数のコンポーネントを置いても待機時のコストが増えないこと（§6.8 の `WithData` 方式と `revision` 監視で担保）
- **メモリ：** 作業用バッファ（`BakeMesh` 結果、スキニング行列キャッシュ、パラメータ化スナップショット）はセッション中のみ保持し、終了時に解放する
- **安全性：** 元メッシュアセットへは決して書き込まない。ベイクのみが唯一のディスク書き出し経路
- **エラー耐性：** NDMF が無い／プレビューが無効／頂点数不一致、いずれも例外を出さずに縮退動作する

### 流用の実績

§13 のマップどおりに実装した。**11 ファイルは型名の置換だけで通り、ロジックには一切手を入れていない。**

| 状態 | ファイル |
| --- | --- |
| **そのまま流用**（識別子の置換のみ） | `MeshEdit` / `MeshDeltaApplier` / `ProxyRegistry` / `LiveEdits` / `DownstreamGuard` / `DenLatticePreviewNode` / `DenLatticePreviewFilter` / `DenLatticePlugin` / `DenLatticeBaker` / `DennokoVersionChecker` / `DenLatticeVersion` / `DenLatticeLocalization` |
| **構造を流用して中身を差し替え** | `EditSession`（ライフサイクル・Undo 規律・確定処理・警告表示は DME のまま、選択とドラッグ配分だけラティス化）/ `EditSession.State`（遮蔽・スクリーン座標キャッシュを削除し、ボックス内判定を追加）/ `EditSession.Overlay` / `DenLatticeInspector` |
| **新規** | `LatticeBasis`（基底評価）/ `LatticeResampler`（格子数変更）/ `EditSession.Lattice`（ボックス・パラメータ化・影響計算）/ `EditSession.Rendering`（ケージ描画）/ `DenLattice`（コンポーネント）/ `VectorBlob` / Enums |

NDMF 連携・データ保持・Undo・ベイク・プレビュー・バージョンチェック・ローカライズはすべて DME の資産で賄えている。**プレビューとビルドの適用処理は DME と完全に同一のコード**であり、ラティスの評価はビルドパスに一切現れない。

### 設計からの差分

- **オーバーレイの項目。**初版では補間方式・ボックスの自動配置もパネルへ置いていたが、パネルがシーンを覆いすぎるため Inspector へ移した（§6.7）。パネルに残すのは、変形しながら何度も切り替える格子数・ミラー・ボックス操作だけ
- **格子数変更時のケージ。**初版は旧いケージをリサンプルして形を保っていたが、細かくした直後に「歪んだケージのどこを掴むのか」が読めなくなるため、格子位置へ戻す方式へ変更した（§12 A）
- **制御点の遮蔽表示。**要件では「メッシュに隠れた制御点は減光して描く」としていたが、実装では常に手前へ描いている。制御点は空間中に浮いており、深度比較で減光しても掴めるかどうかが分からなくなるため。密集時の見分けは、選択中を二重円にすることで代替した
- **「境界の制御点を固定」の削除。**三次基底では境界の変位が厳密にゼロにならず「段差が消える」と言えるのは三線形のときだけで、既定の 3×3×3 では ON にすると中心 1 点しか動かせない。説明の難しさに対して使える場面が狭いため機能ごと落とした
- **Undo の記録方式。**`Undo.RecordObject` はシリアライズ内容量に比例した PropertyModification の生成・照合を行うため、1 ドラッグでボックス内の全頂点を書き換える本ツールでは Ctrl+Z が数百ミリ秒止まる。バイナリのスナップショットを積む `Undo.RegisterCompleteObjectUndo` へ統一した（→ `Editor/Core/DenLatticeUndo.cs`）

### 未検証項目（Unity 上で確認が必要）

1. 制御点 1000 点でのシーンビューの応答（→ §12 E）
2. 矩形選択が `hotControl` を一時的に取ることによる、シーンビューの他操作との干渉
3. オーバーレイの高さの実測（`GUILayoutUtility.GetLastRect` による自動フィットが 1 フレーム遅れで収束するか）と、パネル下でハンドルを止める `AddControl(..., 0f)` の効き
4. MA Scale Adjuster 併用時に、ケージが素の状態のうちだけパラメータ化が追従する挙動（§7.4）
5. NDMF プレビュー越しの複数 Renderer 同時変形（服＋素体）
